Kubernetes

cert-manager certificates from your ADCS, with no plugin

Workloads in a cluster often get their certificates from a CA the cluster keeps for itself, which nothing outside the cluster trusts. cert-manager's built in ACME issuer can ask Ducks in a Row instead, and the certificates then chain to the ADCS root your organisation already trusts. The cluster needs no plugin, holds no Active Directory account and no rights on the CA, and one scoped credential decides which names it may order.

An ordinary ACME Issuer

Each certificate template is its own ACME directory, so an Issuer points at the template it should issue from. The dashboard writes the manifest for you: create a credential on the ACME page and pick cert-manager in the setup panel. It produces an Issuer like this one, a kubectl create secret line for the key, and a sample Certificate whose key already matches the template.

apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: ducks-in-a-row
  namespace: team-a
spec:
  acme:
    server: https://ducks.corp.example.com:5001/acme/WebServer/directory
    caBundle: <base64 of your CA root, PEM>
    email: you@example.com
    privateKeySecretRef:
      name: ducks-account-key
    externalAccountBinding:
      keyID: <key id from the dashboard>
      keySecretRef:
        name: ducks-eab
        key: secret
    solvers:
      - http01:
          ingress:
            ingressClassName: nginx

Each team to its own names

Give each team's namespace its own Issuer and each team its own external account binding credential, with a domain namespace that lists the team's domains. A team can then order only its own names, and revoking one team's credential leaves the others alone. If one platform team owns every name, a single ClusterIssuer with one credential is simpler.

What it asks of your network

  • cert-manager 1.11 or later, and your root in caBundle, so cert-manager trusts the server's own certificate from your CA.
  • For http-01, an ingress that answers plain HTTP on port 80, reachable from the Ducks in a Row server, whose DNS resolves the certificate names to that ingress.
  • For wildcards, dns-01 into a zone the server's DNS servers answer from.
  • Your internal zone resolvable inside the cluster, because cert-manager checks the challenge itself before it tells the server it is ready.

By default cert-manager renews at two thirds of the lifetime the template gave the certificate. From cert-manager 1.21, with the ACMEUseARI feature gate switched on, it also reads the server's renewal information, so a revoked certificate is renewed at once.

What has been run

Our regular test cycle runs cert-manager against a real ADCS certificate authority: a namespaced Issuer, a Certificate with an RSA key, the Ingress annotations, http-01 through ingress-nginx, and dns-01. Not yet run against Ducks in a Row: caBundle, external account binding, a ClusterIssuer, an ECDSA template, renewal and ARI, and anything on OpenShift. The Kubernetes guide marks each of these where it comes up, and says what is known about OpenShift.

Part of the free core

The ACME server and external account binding are part of the free core: free in production, with no limit on certificates, for one CA. Ducks in a Row is source available under the Business Source License 1.1, and it collects no telemetry.
